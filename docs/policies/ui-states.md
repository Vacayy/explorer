# 정책: UI 상태 정의

> 모든 화면/컴포넌트는 아래 5가지 상태를 반드시 정의해야 한다.

---

## 5가지 상태

### 1. Empty State (데이터 없음)
- **언제**: 첫 사용, 조건 검색 결과 0건, 미입력 데이터
- **표시**: 설명 메시지 + 액션 유도 (CTA 버튼)
- **금지**: 빈 테이블/차트를 그대로 보여주지 않는다

| 화면 | Empty 메시지 | CTA |
|------|------------|-----|
| 워치리스트 | "관심 종목을 추가해보세요" | [산업군 탐색] [종목 검색] |
| 스크리너 결과 0건 | "조건에 맞는 종목이 없습니다" | [필터 초기화] |
| 투자메모 (기업 미선택) | "기업을 선택해주세요" | 워치리스트 종목 퀵 버튼 |
| 투자메모 (메모 없음) | "첫 번째 투자 논점을 작성해보세요" | [+ Bull 추가] |
| 시그널피드 (워치리스트 빈) | "워치리스트에 종목을 추가하면..." | [워치리스트로 이동] |
| 사업정보 | "데이터 추가 버튼으로 입력해주세요" | [+ 데이터 추가] |

### 2. Loading State (로딩 중)
- **언제**: API 호출 중
- **표시**: 실제 레이아웃 형태의 스켈레톤 shimmer (회색 블록 애니메이션)
- **금지**: "로딩 중..." 텍스트만 보여주지 않는다

| 컴포넌트 | 스켈레톤 |
|---------|---------|
| KPI 카드 6개 | `KpiSkeleton` — 6칸 그리드 + 제목/값/서브 블록 |
| 차트 | `ChartSkeleton` — 제목 바 + 큰 사각형 블록 |
| 테이블 | `TableSkeleton` — 헤더 바 + N행 바 |
| 시그널 피드 | 카드 3개 스켈레톤 |

### 3. Partial State (부분 로딩)
- **언제**: 여러 API를 병렬 호출할 때, 일부만 먼저 도착
- **정책**: 먼저 도착한 데이터부터 순차 렌더링. 나머지는 각각 스켈레톤 유지.
- **예시**: 요약 페이지에서 KPI 카드(빠름) → 차트(느림) → 공시(느림) 순서로 표시

### 4. Error State (에러)
- **언제**: API 호출 실패, 네트워크 오류, 서버 에러
- **표시**: `ErrorState` 컴포넌트 — 메시지 + [다시 시도] 버튼
- **금지**: 에러를 무시하고 빈 화면을 보여주지 않는다. console.error만 찍고 UI는 정상인 척하지 않는다.

| 에러 유형 | 메시지 |
|---------|--------|
| 네트워크 오류 | "서버에 연결할 수 없습니다. 백엔드가 실행 중인지 확인해주세요." |
| 404 (기업 없음) | "기업 정보를 찾을 수 없습니다." |
| 500 (서버 에러) | "데이터를 불러오는 중 오류가 발생했습니다." |
| DART API 한도 | "일일 API 호출 한도에 도달했습니다. 내일 다시 시도해주세요." |

### 5. Ideal State (정상)
- **언제**: 데이터가 정상적으로 로드됨
- **정책**: 가장 마지막에 설계. 1~4번을 먼저 정의한 후에 정상 화면을 설계한다.

---

## 적용 체크리스트

새 컴포넌트를 만들 때 아래 5개를 모두 확인:

```
□ Empty: 데이터 없을 때 무엇을 보여주는가?
□ Loading: 스켈레톤이 실제 레이아웃과 비슷한가?
□ Partial: 병렬 로딩 시 먼저 온 데이터가 표시되는가?
□ Error: 실패 시 사용자가 무엇을 할 수 있는가?
□ Ideal: 정상 데이터 표시
```

# 데이터 신선도 점검 (D-222)

## 문제

작업은 종료 코드 0으로 끝나도 결과가 비거나 묵을 수 있다. 2026-10 기준 실제로 겹친 사례:

- 일별 시세가 16:35에 `marketStatus=OPEN`을 만나 105종목만 저장(10-12·13) — 종료 코드 0
- 발견용 시세 이력이 스케줄 없이 9-18에 정체 — 발견 결과가 4주 묵은 시세로 판정
- 시장 국면(`snapshot_market`)이 launchd에 등록되지 않아 9-10 이후 정체

모두 화면이 아무것도 말하지 않아 사용자가 결과를 보고 알아챘다. 그래서 감시 대상을 작업이 아니라 **저장된 결과 데이터의 최신 시점**으로 잡는다.

## 계약 (`backend/pipeline/health.py`)

항목 레지스트리 `CHECKS`: (키, 라벨, 종류, 최신 시점 SQL, 기준, 채우는 곳, 경고 여부).

| 종류 | 기대 시점 | 지연 판정 |
|---|---|---|
| `trading` | KOSPI 지수 일봉(`index_kospi`)에 있는 최근 거래일. 오늘이면 마감 처리 시각(`ready`, KST) 뒤에만 | 최신 시점 이후 확인된 거래일 수 ≥ 1. 지수 달력에 없는 날(휴장·대체공휴일)은 세지 않는다 |
| `age` | 최대 경과 시간(h) | 경과 > 기준. 노트북 수면 뒤 따라잡기 여유를 둔다 |
| `launchd` | `launchctl list`의 `dev.explorer.*` 마지막 종료 코드 | 0이 아닌 것 |

- 일별 시세는 날짜가 최신이어도 그날 저장 종목 수가 직전 5거래일 중앙값의 90% 미만이면 지연이다(105종목 사례).
- 지수 달력 자체가 묵으면 거래일 판정도 멈추므로 `indices` 항목(경고)이 따로 잡는다.
- 상태: `ok`·`stale`·`error`(조회 실패). LLM 0, 읽기 전용.

현재 항목: 국내 일별 시세·발견용 시세 이력·시장 국면·피드 문서 유입·주요 지수(경고) / 리스크 지표·종목 묶음 감시·거래대금 상위·30분 체인·매크로·미국장 브리핑·DB 백업·예약 작업 종료 코드(관리자 화면만). 새 수집·생성 작업을 추가하면 이 레지스트리에 결과 테이블 한 줄을 함께 등록한다.

## 화면

- **관리자 `/admin` 상단 '데이터 신선도'**: 모든 항목의 상태·최신·기대·채우는 곳 표. `GET /api/spine/admin/health`. 로딩 Skeleton, 실패 ErrorState, 항목은 항상 있으므로 빈 상태 없음.
- **홈 브리핑**: 경고 항목 중 지연이 있으면 LLM 경고 다음에 "데이터 갱신 지연 — …" 한 줄(`/admin` 링크). 방문마다 계산하므로 `launchctl`은 부르지 않는다.
- **텔레그램 아침 브리핑**: 같은 한 줄을 LLM 경고 다음에 둔다(D-111의 '메타 경보만 최상단' 예외와 같은 성격).

## 검증

`backend/tests/test_health.py` — 휴장일 제외·마감 전후 기대일·105종목 부분 저장·경과 시간·경고 대상 한정. 실DB: 시장 국면 19거래일 지연, 리스크 10거래일 지연을 잡음(나머지 최신) → `snapshot_market`을 launchd `market`(평일 16:20)으로 등록하고 실행해 둘 다 최신으로 복구. 홈 응답과 텔레그램 본문 조립에서 경고 한 줄 확인(발송 안 함).

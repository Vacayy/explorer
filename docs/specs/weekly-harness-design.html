실행·판단 갱신·개선은 서로 다른 상태를 바꾼다

실행루프: State → Context 구성 → Model decision → Action control → Environment → Observation/작업 평가 → State. State는 질문·작업·근거·판단·예산의 전체 상태이고 Context는 이번 역할에 필요한 입력이다. ContextSnapshot에는 정책 버전, 포함한 state/근거 ID, 제외·압축 이유와 상한을 남긴다. 모델은 ActionProposal을 제출하고 코드는 요청 형식·권한·시점·전제 상태를 검사한다. 모델 호출·도구·하위 작업의 전체/작업별 예산을 예약·정산하며 timeout을 집행한다. 허용된 읽기·검색·계산은 자동 통과하고 추가 권한이 필요한 요청만 별도 권한 상태로 남긴다. 거절·실패·대기도 관측이며 재시도와 종료의 근거가 된다.

주간 판단 갱신: 새 사건과 후속 관측으로 전망·가정·다음 확인 조건을 ThesisVersion에 갱신한다. 같은 하네스 버전에서도 수행한다. 과거 AI 의견은 독립 증거가 아니며, 시장 방향 예측의 실패와 하네스의 조사·판단 결함은 구분한다.

개선루프: 실행 기록/평가 → FailureRecord → ChangeCandidate → 독립 비교 검증 → 새 주차 병행 확인 → ReleaseRecord → 이후 실행의 관측으로 연결한다. 이번 리포트를 수정하는 작업과 다음부터 사용할 방법을 바꾸는 작업을 구분한다. 개선 작업은 별도 예산과 상태를 가지며 실행 중 설정을 고치지 않는다.

계약필수 내용과 판정

ChangeCandidate기준 버전, 실패 근거, 정확한 diff, 영향 범위, 기대 효과, 악화 금지 항목, 실험 예산·담당·복귀 대상·ValidationPlan. prompt/방법, context/검색, tools, model, orchestration/제어 정책을 대상으로 함. 계획 미완성은 prepared로 전환하지 않음.
ValidationPlan사례·cutoff·근거/초기 기억·기준/후보 버전·evaluator/rubric 버전·반복 수·성공 기준·악화 허용 범위·비용/지연 상한을 실행 전 고정. 수치 기준은 pilot으로 보정 후 본 비교 전에 고정하며 결과를 보고 완화하지 않음.
EvaluationResult계약 검사 → 알려진 실패 사례 회귀 → 미사용 주차의 짝지은 블라인드 비교. 중대한 근거·수치·시점·버전·예산 오류는 차단. 핵심 논쟁·자체 의견·반론·대응의 전문가 정보 가치와 비용을 함께 평가. 모든 반복·실패를 보고하고 부족한 근거는 inconclusive.
ShadowResult사용자에게 전달하는 버전은 유지한 채 사전 기간·표본·예산·기준으로 새 주차에서 병행 비교. 실패는 수정/기각, 불확실은 보류. 자동 리포트 검토 통과와 후보 채택 판정은 별개.
HarnessVersion코드·상태 스키마·역할 프롬프트·분석 방법·context/검색 정책·도구 스키마/구현·모델 식별자/설정·행동/예산 정책을 불변 manifest와 hash로 묶음. 자료·초기 기억·평가 버전은 별도 참조.
ReleaseRecord독립 컨트롤러가 후보·비교/병행 결과·현재 active와 비교 기준의 일치·모델/도구 가용성·상태/복귀 호환성을 검증. 정책 통과 시 active 참조를 원자적으로 변경. 제안 모델은 active와 평가 판정에 직접 쓰지 않음.

비교의 공정성과 평가 독립성: 검색·도구 변경은 같은 검색 가능한 corpus/원시 관측에서 각 버전이 자체 조사한다. 선정 packet 고정은 context·집필의 부분 실험에만 쓰고 전체 결과를 별도로 평가한다. 같은 초기 기억을 주며 주간 연쇄 평가의 기억은 버전별로 분리한다. 기준 원문·숨겨진 판정값은 생성 context와 후보 작성 작업에서 제외한다. 진단에 공개한 사례는 개발 세트로 이동하고 독립 표본을 보충한다. 평가 기준의 수정은 별도 evaluator 버전으로 기준/후보 양쪽을 재평가한다.

상태 전이: 후보는 proposed → prepared → evaluating → validated / rejected / inconclusive. 변경하면 revision을 올리고 기존 판정을 보존한다. validated 후보도 병행 확인과 릴리스 판정을 거친다. 릴리스 이력은 released → rolled_back / retired이며 active 참조와 불변 버전을 분리한다.

채택·롤백: 새 실행만 시작 시 active를 읽어 run.manifest에 고정하고 하위 작업·재개까지 같은 버전을 유지한다. 채택 후 중대한 결함이나 사전 운영 기준 위반이 확인되면 새 실행 배정을 멈추고 호환되는 이전 버전으로 active를 복귀한다. 기존 작업은 원 버전으로 계속하거나 명시적으로 취소한다. 과거 근거·결과·시장 판단은 삭제/덮어쓰기하지 않는다. 이전 모델·도구가 없거나 상태 호환성이 부족하면 강행하지 않고 신규 실행을 중단한다. 모델 버전을 고정할 수 없는 공급자는 관측 가능한 식별자와 재현 한계를 기록한다. 이 release는 하네스 구성의 채택이며 리포트 발행·모델 재학습과 구분한다.

현재 범위와 다음 구현: 기존 로그·입력 hash·비교 평가·재개를 재사용할 설계 계약이다. 버전/context/관측 연결을 먼저 마련하고 아래 조사·집필 구조를 구현한 뒤 후보 비교·병행 확인·active 전환·롤백 실행기를 연결한다. 이번 작업에서 자동 개선·릴리스를 구현하거나 후보 실험·버전 채택을 실행하지 않았다. 결정 이유 D-172.

실행루프 안에서 수행하는 브리핑 업무

  1. 브리핑 책임자의 의제 선정

    시장·기업 관측, 새 사건, 전문 소스의 논쟁, 지난 판단·열린 질문에서 변화 제보를 모은다. 판단·대응 영향, 새로운 정보, 설명의 공백, 시간의 촉박함으로 통상 2–4개 질문을 고른다. QuestionBrief에는 선정 이유, 검증할 설명, 필요한 자료·기간, 예산, 완료 조건을 넣고 미선정 주요 변화도 기록한다.

  2. 질문마다 배정하는 조사자와 분석 방법

    분야별 기록은 지속 상태로 남기고 조사자는 작업마다 호출한다. 프로필·인물·본문·사건·기간 검색을 병행하며 원문과 전후 글을 읽는다. 사전 기대/실제 반응, 사건의 시작/지속/해소, 기업 전망 변화, 가격/경쟁 시나리오의 분석 방법을 조합한다. ResearchMemo는 자체 의견과 지지·반박 원문, 기간·공통 가정, 미해결 질문을 제출한다. 첫 의견은 다른 조사자의 결론을 보기 전에 작성한다.

  3. 결론 전 전문 검토와 실제 재조사

    전문 검토자는 원문·기간·가정·계산을 대조해 핵심 논쟁 누락과 반론을 찾는다. 중요한 공백은 담당·결론 영향·필요 관측·완료 조건이 있는 ResearchRequest로 보낸다. 근거는 조사, 수치는 도구, 해석은 종합 또는 추가 조사, 문장은 집필로 반환한다. 책임자가 반론의 채택·기각 이유를 기록한다.

  4. 동일 책임자의 최종 판단

    종합 단계는 의제 선정과 같은 책임 역할의 별도 호출이다. 시장 진단, 버팀목·취약 지점, 가격과 부합하는 시나리오, 다음 주 대응과 변경 조건을 DecisionBrief로 고정한다. 다수결을 하지 않고 이견을 보존한다. 시장 기대의 직접 관측, 출처 의견, 우리의 추론을 구분하고 임의의 반영률·보유 비중·매매 기준을 만들지 않는다.

  5. 집필과 서로 다른 두 검토

    집필자는 고정한 판단·선정 원문·계산·차트와 사용자 작문 기준으로 전문가 브리핑을 쓴다. 새 자료나 의견이 필요하면 상위 단계에 요청한다. 전문 검토는 본문·판단·원문으로 사실·논증·대응 조건을 확인하고, 독자 검토는 본문만으로 맥락·의견·대응의 명료성을 확인한다. 코드 검사는 출처·수치·시점·버전을 점검한다. 수정 뒤 관련 판단과 최종 본문을 다시 검사한다.

  6. 연구 작업 공간과 주간 판단 갱신

    EvidenceSpan → Claim/계산 → ResearchMemo → DecisionBrief → 본문 문단의 의존관계를 저장한다. 발견·읽음·채택·기각·미확인을 분리하고 원문 전문을 재확인할 수 있게 한다. 근거 버전이 바뀌면 의존한 결과를 재검토한다. ThesisVersion에는 이전 기대·현재 판단·변경 근거·다음 검증 조건을 저장하며, 초안·발행 판단·후속 결과를 구별한다. 과거 생성 판단은 증거가 아니다.

실행 계약: 모델 역할 5개(책임자·조사자·전문 검토자·집필자·독자 검토자)와 코드 실행기를 분리한다. 기존 동결 corpus, 검색/읽기·계산·공급자, 입력 hash·예산·취소·재개를 재사용한다. 전체 및 질문별 예산, 동시 작업 상한과 스키마가 정해진 이벤트를 사용한다. 핵심 공백이 남은 예산 종료는 미완성 초안이며 자동 검토 통과·전문가 평가와 구분한다.

시점·추가 자료: 회고 기간·대응 기간·정보 기준시각·실제 수집 시각을 분리한다. 기존 corpus는 불변이며 초기 조사 중 적격 외부 확보는 추가 전용 묶음과 manifest로 고정한다. 당시 버전 미확인 자료는 과거 시점 판단에서 격리한다. 재개는 확정 자료만 사용하고 새 외부 확보는 별도 분기 실행으로 남긴다. 프로필·태그·과거 판단도 이용 가능 시점으로 제한한다.

구현·품질 기준: 버전·context·관측 계약 → 질문·근거·재조사 연결 → 종합·집필·검토 → 주간 갱신·필요 공급자 확장 → 후보 검증·병행 확인·채택/복귀 순서로 구현한다. 동일 corpus·비교 가능한 예산에서 발견→읽기→논증 활용→최종 의견 반영을 추적한 뒤 미사용 주차의 전문가 블라인드 평가를 수행한다. 특정 모델·프레임워크 전면 이전, 고정 찬반 토론, 데이터 공급자 확대부터 시작하는 대안은 선택하지 않았다. 근거는 리서치 조직 조사와 금융 AI 조사, 결정 이유는 D-171·D-172에 남긴다.

웹 탐색은 현재의 직접 URL 읽기에 검색·원 출처 추적을 추가하는 방향입니다. 결과의 시각·본문을 확인하고 실제 확보분을 실행에 고정합니다. 기존 스냅샷과 실행 기록을 바꾸지 않으며, 재개 중 새 자료가 필요하면 자료 추가와 기준시각 변경 여부를 명시한 파생 실행으로 다룹니다. 당시 버전이 입증되지 않는 사후 자료는 과거 재생의 빈칸을 채우는 데 쓰지 않습니다.

D

책임은 분명하게, 구조는 실험으로 결정한다

필요한 것은 분석·작성·검증의 책임과 입력 경계입니다. 이를 각각 영속 에이전트로 만들 필요는 없습니다. 첫 후보는 하나의 분석 책임자가 조사와 판단을 맡고, 독자용 작성과 평가를 별도 문맥에서 수행하는 구조입니다. 더 단순한 한 번의 작성이 같은 품질이면 그쪽을 채택합니다.

연구 작업 공간

주간 시장 지도, 조사할 쟁점, 확보한 근거와 계산, 대안 설명, 잠정 판단의 변경 이력. 실패한 도구·버린 해석도 보존합니다.

현재 판단 요약

이번 주의 시장 진단, 중요한 변화, 선택한 해석과 반대 근거, 대응·전환 조건, 해석에 필요한 인용 문맥. 장황한 조사 이력은 넘기지 않습니다.

독자용 브리핑

자연스러운 제목·문단·차트·각주. 작성 단계에서 새로운 사실이나 대응을 꾸며내지 않습니다. 판단 요약 자체가 부족하면 연구 단계로 돌려보냅니다.

작성자를 추가해도 분석 책임이 사라지지 않습니다. 작성 단계가 바꾼 해석·대응은 분석 책임자의 확인을 거칩니다. 본문의 숫자와 사실은 최종 문장 위치에 근거를 연결하고, 한 문단 안의 사실과 해석도 각각 추적할 수 있게 합니다. 모든 문단을 한 종류의 Claim으로 제한하는 현재 방식은 재검토합니다.

검토는 두 질문에 답해야 한다

사실·논증 검사

계산·단위·시간·인용 지지 범위, 다른 설명의 누락, 근거와 대응 강도의 관계를 검사합니다. 합리적인 조건부 판단에 인과관계의 완전한 증명을 요구하지 않습니다. 지적이 과도하면 근거를 들어 판정도 재검토합니다.

임의 숫자와 정밀한 척하는 확률은 막습니다. 숫자 포맷의 책임을 한 곳에 두고 최종 HTML 텍스트까지 검사합니다.

투자자 관점의 평가

최종 본문만 읽고 시장 상태·우선 의견·현재 대응·전환 조건을 복원해 봅니다. 원문과 실제 판단 요약을 별도로 대조해, 읽기 쉽지만 근거 없는 의견이나 편집 중 달라진 대응을 찾아냅니다.

연구 기록을 열어야 의견을 알 수 있거나, ‘가능하다·확인한다’만 남거나, 지난주 회고가 없다면 다시 씁니다. 필드의 존재나 문체 점수만으로 통과하지 않습니다.

검토 뒤 사실·의견·대응이 바뀌면 해당 근거와 최종 본문을 다시 검사합니다. 제한된 수정 횟수 안에 해결되지 않으면 보고서 미완료로 남깁니다. ‘실행 종료’, ‘독자용 품질 통과’, ‘실제 공개’를 별도 상태로 관리해 오류가 남은 작업 초안을 완성 Weekly의 대표 결과로 내놓지 않습니다. 핵심 판단을 해치지 않는 공백과 치명적인 공백은 구분합니다.

현재 코드에 적용할 경계

유지·재사용바꾸거나 추가이유
store.py·worker.py·CLI/API의 실행·취소·복구작업 시도와 공개된 주차의 이력 구분, 버전별 보고서 저장복구 기능은 유용하다. 재시도를 ‘지난주’로 잘못 서술하는 것은 차단해야 한다.
evidence.py·원문 hash·시점 경계·출처 계보주간 경계, 사건 묶음, 시장 전체 조사 자료, 원 출처 검색과 문서/차트 읽기자료의 신뢰 경계는 유지하고 조사 범위를 넓힌다.
calculations.py의 재현 가능한 계산질문에 필요한 지표만 선택, 비교 가능한 세션·표본 확인, 개별 수치의 최종 표기 검사모든 질문을 수익률·기울기 비교로 바꾸지 않는다.
runner.py의 예산·checkpoint시장 지도 → 조사 의제 → 판단·대응 → 독자용 작성으로 입력과 종료 기준 재설계읽기·계산 횟수 대신 판단의 완결성을 관리한다.
현재 원문·수치 검사와 검토 로그models/weekly.py·review.py·render.py의 독자용 계약과 검토 방식 변경근거 추적을 유지하면서 자연스러운 문장과 명확한 의견을 전달한다.
evaluation.py의 입력 고정·비교 산출물충분한 자료의 비교, 자동 조사 비교, 독자 평가, 수정 전후 유용성 감소 탐지기존 ‘같이 읽은 3개 문서’ 비교만으로 조사 능력을 평가할 수 없다.

보고서 계약은 버전을 올리고 기존 실행·초안·평가 파일은 그대로 읽을 수 있게 합니다. 운영 수집 DB와 다른 진행 작업은 보존합니다. 다음 주 기억은 실제로 전달된 이전 판단과 그 후 관측을 연결하며, 보류된 초안은 공개 이력으로 취급하지 않습니다.

E

좋은 글을 쓸 수 있는지와, 필요한 자료를 찾는지를 따로 시험한다

이전 실패를 단순히 더 긴 프롬프트나 더 많은 호출로 덮지 않습니다. 어디를 고치면 실제 독자용 품질이 나아지는지 구분할 실험을 먼저 합니다. 아래 표본 수·판정 문항은 초기 제안이며 아직 성능 측정 결과가 아닙니다.

실험 1 · 충분한 같은 자료로 작성 방식 비교

처음 한 주차는 에이전트가 골랐던 3개 문서에 한정하지 않고, 주요 시장 변화와 쟁점을 다룰 수 있는 근거 묶음을 개발 단계에서 준비합니다. 자료 정리는 기준 입력을 만드는 일회성 작업이며 매주 사람이 핵심 분석을 대신하는 운영 방식을 뜻하지 않습니다. 자료를 더 주었다고 완전한 정보를 가정하지 않고 남은 중요한 공백을 기록합니다.

비교군실행확인할 질문
A · 단일 작성같은 원문·계산 묶음과 독자 요구로 한 번에 완성 브리핑 작성단순한 방식만으로 이미 충분한가?
B · 판단 후 작성시장 진단·우선 해석·대응을 먼저 정하고, 별도 문맥에서 근거와 함께 글로 구성판단 정리가 논증과 대응을 실제로 개선하는가?
C · 판단·작성·이중 검사B에 사실·논증 검사와 투자자 평가를 적용하고 제한 수정오류를 줄이면서 의견과 가독성도 유지하는가?

같은 기준시각·자료·모델 후보·독자 요구를 고정하고 호출 수·토큰·시간·공급자 추정 비용을 기록합니다. B·C의 추가 호출 비용도 결과에 포함하고, 비슷한 총예산의 단일 작성과 재실행 비교를 후속으로 붙입니다. 기존 실패본은 회귀 사례로 보존하되 입력 자료가 다르므로 새 결과와의 차이를 전부 구조 개선의 효과라고 주장하지 않습니다.

선택 규칙: A가 비슷한 품질이면 A를 채택합니다. B가 핵심 판단 재작성 부담을 줄일 때 분리합니다. C에서 사실 오류는 줄었지만 대응이 사라지면 검사 설계를 고칩니다. 어느 방식도 충분한 자료로 좋은 Weekly를 못 쓰면 자동 조사기를 확장하기 전에 판단 지침·모델·작성 계약을 수정합니다.

실험 2 · 근거 확보를 에이전트에게 맡기기

선택한 작성 방식은 고정하고, 같은 시점의 허용 자료 풀에서 에이전트가 시장을 훑고 필요한 근거를 직접 찾게 합니다. 실험 1의 준비된 자료와 비교해 빠진 핵심 변화, 잘못 고른 질문, 읽지 않은 반대 근거, 판단·대응의 차이를 봅니다. 문서 수와 도구 호출 수는 진단용 기록이며 성능 점수가 아닙니다. 자료가 준비되면 잘 쓰고 자동 조사에서는 실패한다면 조사·접근 경로를 고칩니다.

평가의 실제 절차

  1. 조건명을 가린 최종 본문을 사용자 또는 투자 리서치 경험이 있는 평가자가 먼저 읽습니다. 시장 상태·의견·현재 대응·바꿀 조건을 짧게 적고 ‘핵심 판단을 다시 써야 하는가’를 판정합니다.
  2. 근거 묶음을 열어 중요 누락, 사실·시간·수치 오류, 단정의 강도, 선택한 설명과 대응의 정합성을 점검합니다. 읽기 좋은 글이 사실 오류를 상쇄하지 못합니다.
  3. 작성 전 판단과 검토 전후 본문을 대조합니다. 개선인지, 주장만 삭제해 내용이 비어버렸는지 기록합니다. 모델 평가는 보조이며 사용자 평가를 자동 대체하지 않습니다.
  4. 일부 근거를 제거하거나 반대 관측을 넣은 통제 사례에서 해당 판단과 대응만 합리적으로 달라지는지 봅니다. 자료가 바뀌어도 항상 같은 강세·관망 결론이면 실패입니다.

중대한 사실·시간·계산 오류가 없고, 핵심 변화·의견·대응의 재작성이 필요 없으며, 중요한 반대 근거를 다뤘을 때 통과 후보로 봅니다. ‘의견 필드가 있음’, 인용 개수, 문체 점수의 합계로 대체하지 않습니다. 길이는 읽는 데 도움이 되는 범위에서 실험하며 고정 글자 수를 성공 기준으로 삼지 않습니다.

한 원문에 맞춘 모방을 피한다

기준 Weekly는 문제 선택·근거 연결·대응의 표현을 분석하는 개발 사례입니다. 저자의 방향성이나 단정까지 정답으로 고정하지 않습니다. 프롬프트 예시는 다른 주차 또는 추상화한 분석 원칙을 쓰고, 평가 대상 주차의 원문 결론은 생성 입력에서 제외합니다. 개발용 2개 주차, 미사용 3개 주차, 앞으로 공개 전에 고정하는 2개 주차를 초기 표본으로 제안합니다. 추세·횡보·충격·주도주 교체·뚜렷한 기회가 없는 상황을 포함합니다.

현재 확보한 기준 원문에는 주간 회고와 이후 추가 문단이 섞여 있습니다. 현재 보존된 9월 15일 스냅샷을 9월 11일 당시 시스템 입력이라고 부르지 않습니다. 과거 자료의 당시 버전을 증명할 수 없으면 재구성 실험으로 표시하고, 엄격한 시점 평가는 이후 실제 확보한 주차로 대체합니다. 사전 기록한 판단을 다음 주와 연결하되, 한두 번의 수익률로 전문성을 판정하지 않습니다.

F

구현은 완성 브리핑을 먼저 검증하는 순서로 진행한다

첫 개발 산출물은 새 에이전트 구성도가 아니라, 동일한 주차를 다룬 실제 투자자용 브리핑과 비교 평가입니다. 후속 구현 요청으로 아래 1–2단계의 실행 기반을 만들고 첫 주차의 실제 생성과 비교 기록까지 완료했습니다. 자동 조사 연결과 이후 주차 검증은 후속이며, 현재 상태는 LIVE에서 확인합니다.

순서·의존성구체적인 작업·산출물완료 기준·실패 시 조치
1 · 결과 기준 고정원문과 실패본에서 좋은 판단·빈 판단·과잉 확신·무의미한 관망의 사례를 정리. 주간 범위·독자 요구·평가 문항·기존 실패 사례를 고정.같은 자료로 같은 독자 문제를 평가할 수 있음. 원문의 결론 복제나 빈 필드 검사로 평가가 바뀌면 기준부터 수정.
2 · 1 이후, 첫 주차 완성본 비교개발용 근거 묶음을 준비하고 A/B/C 작성 실험. 본문·차트·각주가 있는 실제 HTML 3종과 비용·평가를 남김. 임시 작성 실험만 먼저 만들고 범용 루프 확대는 보류.평가자가 의견과 대응을 이해하고 핵심 논증을 다시 쓰지 않아도 되는 후보가 있음. 없다면 모델·판단·작성 지침을 먼저 바꿈.
3 · 2의 선택 결과 반영현재 판단과 연구 기록 분리, 보고서 계약 버전, 최종 문장 인용, 단위 표기, 공개 주차/재시도 구분. 선택한 작성·검토 방식을 현행 CLI에 연결.내부 정정 이력이 본문에 나오지 않고, 편집 뒤 숫자·의견·대응이 보존됨. 기존 저장 보고서 열람·취소·재개도 유지.

시점과 재개 계약

  • live 기본값은 실행을 시작한 현재 시각입니다. 마지막 미국 주간 마감을 자동 추정하지 않습니다. 관측 기준시각과 실제 버전을 고정한 시각을 별도로 보존합니다.
  • public_reconstruction --cutoff 2026-09-11T16:00:00-04:00처럼 과거 시점을 지정할 수 있습니다. 당시 버전이 미확인된 운영 문서·가격은 검색·읽기·계산에서 격리하고, 공개 vintage 등 확인 가능한 자료만 분석 문맥에 넣습니다. 과거 원문 부족은 부분 완료 또는 실패 사유가 될 수 있습니다.
  • system_replay --replay-run-id RUN_ID --cutoff ...는 요청 cutoff 이전에 실제 고정한 live snapshot만 사용합니다. 이미 소실된 과거 원문을 재생한 것으로 표시하지 않습니다.
  • 재개는 같은 원문과 계산 입력을 유지하고 도구·시간 예산을 명시적으로 늘립니다. 재개 중 외부 확보는 닫히며, 새 자료는 새 실행에서 확보합니다. 실행 중 취소는 모델/공급자 프로세스 그룹을 종료하고 다음 호출을 막습니다.
  • 순수 GET은 생성·수집·실험 DB 초기화를 하지 않습니다. 실행/취소/재개/복구는 명시적 POST 또는 CLI 명령으로 처리합니다.

분석의 방향과 최종 판단을 한 곳에서 책임지고, 조사·계산·검증은 명시적인 인터페이스로 분리합니다. 초기에는 분석자 하나와 별도 문맥의 검증 호출로 시작하고, 병렬 조사자는 평가 결과에 따라 추가합니다. [P01]

모델이 결정할 것

무엇이 이상하거나 중요한지, 어떤 설명들이 경쟁하는지, 어느 조사로 구분할 수 있는지, 더 조사할 가치가 있는지, 어느 정도로 결론을 한정할지 결정합니다. 산업별 참고 지식은 질문 후보와 메커니즘을 제공하며 현재 사실을 대신하지 않습니다.

04

분석이 진행되는 방식

정해진 지표 순서를 따르는 대신, 현재 설명에서 부족한 연결을 찾아 다음 조사를 선택합니다. 다음 순서는 기본 실행 흐름이며, 새로운 증거가 나오면 앞 단계로 돌아갈 수 있습니다.

전문성은 어디에서 가져오는가

모델의 일반적인 경제·산업 지식에 더해, 검증한 분석 원칙과 소수의 좋은 조사 사례를 문맥으로 제공합니다. 예를 들어 금리 변동의 배경, 수준과 기대 변화, 상대 성과와 실제 자금 흐름, 계획과 집행의 구분을 조사 지침으로 사용합니다. 현재 상황의 사실과 원인 판정에는 매번 새 근거가 필요합니다.

참고 사례에는 결론뿐 아니라 어떤 증거가 설명을 약화시켰는지와 실패 사례를 함께 둡니다. 평가용 주차의 원문 결론은 이 사례집에서 제외합니다. 초기에 별도 모델 학습을 전제하지 않고, 모델·지침·도구 중 무엇이 오류를 줄였는지 나눠 측정합니다.

  1. 지난 판단과 넓은 시장 관찰을 함께 읽는다

    이전 가설의 갱신 조건부터 점검하고, 가격·시장 내부·거시·기업 행동·수집 담론을 넓게 확인합니다. 자료가 없는 영역은 빈칸으로 남깁니다. 사용자 선택 소스의 언급량을 시장 전체 합의로 확대하지 않습니다.

  2. 핵심 질문 후보와 선택 이유를 남긴다

    시장 해석/대응을 바꿀 중요성, 설명되지 않는 관찰, 경쟁 설명을 구분할 가능성, 자료 상태로 우선순위를 정합니다. 단일 합산 점수는 만들지 않습니다. 선정·보류 이유를 기록하고 조사 중 순위를 바꿀 수 있게 합니다.

  3. 경쟁 설명과 판별 관찰을 연결한다

    각 가설에 메커니즘, 적용 조건, 예상 관측, 반대 근거, 갱신 조건을 둡니다. “금리 상승은 악재” 같은 전제도 이번 상황에 적용되는지 확인합니다. 복수 설명이 함께 작용할 수 있고 어느 쪽도 확인되지 않을 수 있습니다.

  4. 정보를 얻을 가치가 높은 조사를 수행한다

    도구 요청에 “이 결과가 어느 가설을 어떻게 구분하는가”를 한 문장으로 남깁니다. 예상 변경 폭·자료의 직접성·접근 비용을 비교해 원문 확인, 기간 계산, 과거 사례, 신규 확보 중 다음 행동을 선택합니다. 정보 가치의 숫자를 근거 없이 만들지는 않습니다.

  5. 실제 결과를 반영하고 조사 종료를 판단한다

    지지·약화·판별 불가로 근거를 연결하고 필요한 가정의 변화를 기록합니다. 중요한 연결이 검증됐거나, 추가 조사가 판단을 바꾸기 어렵거나, 자료/예산 한계에 도달하면 종료합니다. 반복 검색으로 독립 근거가 늘어난 것처럼 세지 않습니다.

기간 선택 도구의 계약

모델은 기본 거래일 구간, 사건 이후 구간, 변화점 후보 중 질문에 맞는 후보를 제시합니다. 계산기는 수익률·기울기·변동성·낙폭·거래량·이동평균 분산 등을 동일한 정의로 계산하고, 시작점을 이동한 결과를 돌려줍니다. 이 지표들은 진단의 재료이며 보편적인 ‘박스권 판정기’로 취급하지 않습니다.

과거 사례는 두 용도로 나눕니다

메커니즘을 생각하는 사례

어떤 경로가 가능했는지, 현재 무엇을 추가 조사할지 알려줍니다. 서사 검색도 사용할 수 있지만 선정 편향을 인정하고 현재 상승 확률이나 기대수익으로 환산하지 않습니다.

결과 분포를 비교하는 표본

현재 상태·비교 변수·허용 차이·후보 모집단을 먼저 고정합니다. 후보 시점까지의 자료로 선정한 뒤 이후 경로를 따로 엽니다. 실패/횡보, 겹치는 사건과 표본 중복도 기록합니다.

초기에는 검증한 사건 묶음과 수치 조건으로 후보를 좁히고, 관계와 진행 순서를 모델이 대조합니다. 데이터가 충분해지면 순서 기반 유사도 등 검색 방법을 비교합니다. 임베딩 유사도만으로 사례의 적용 가능성을 확정하지 않습니다. 적절한 사례가 없다는 결론도 허용합니다.

과거 재생의 한계

시점 제한과 후보 고정은 선택 과정을 검토 가능하게 합니다. 모델이 학습 중 이후 결과를 이미 알았을 가능성은 제거하지 못합니다. 과거 성적과 앞으로의 사전 작성 성적을 분리해서 보고합니다. [U1, §8.6]

초기 CLI로 같은 실행기를 검증한 뒤 POST 실행, GET 상태/산출물, POST 취소/재개를 추가합니다. 동일 request key로 중복 실행을 막고, 단일 워커부터 시작합니다. SQLite 쓰기 트랜잭션을 모델 호출 동안 유지하지 않습니다.

초기 한도 제안 · 미실측

1회 30분, 분석 선택 24회, 외부/자료 도구 40회, 재검토 2회. 조사와 작성/검증 예산을 분리해 후자를 남깁니다. 이 숫자는 폭주를 제한할 시작값이며 품질·비용 추정치가 아닙니다. 실행 실측 후 조정합니다.

중단과 재개

도구 완료마다 상태를 저장합니다. 취소 시 새 호출을 막고 실행 중 호출은 시간 제한 내 종료시킵니다. 재개는 같은 스냅샷으로 이어가며 새 자료 추가는 파생 실행으로 기록합니다. 한도 종료는 partial이며 완료로 숨기지 않습니다.

구현 순서와 미정 사항

각 단계는 완결된 브리핑을 향해 진행합니다. 새 도구의 개수보다 그 도구가 어떤 분석 실패를 해결했는지를 확인하며 확장합니다.

STEP 01

원문·12개 이미지로 보고된 차트를 재확보하고 실제 목록·수치·주장 연결을 확인합니다. 사용자 목표에 맞는 평가 기준을 작성하고, 보유 자료와 핵심 공백을 원문과 대조합니다. 원문 접근이 안 되면 연결부 개발은 진행할 수 있지만 ‘원문급’ 비교 평가는 미완으로 남깁니다.

완료 조건: 기준 원문/차트 확보, 확인된 분석 요구·오류·해석의 경계와 평가 자료 묶음.
STEP 02

최초의 분석 루프로 완결된 Weekly 작성

스냅샷·기준시각 조회·계산·구간 비교·웹 확보·결정 기록·검증을 CLI로 연결합니다. 실제 질문에 필요한 가격/시점 문제부터 보강합니다. 잠정적으로 핵심 질문 1~2개를 깊게 다루되, 큰 누락은 범위 제한으로 명시합니다.

완료 조건: 원문과 계산까지 추적되는 브리핑, 검증 결과, 부분 실패와 미해결 문제. 이 단계 완료가 제품 품질 통과는 아닙니다.
STEP 03

실패 원인을 분해해 구조를 고친다

같은 자료의 단일 작성·분석 루프·검증 제거 버전을 비교합니다. 문제 선택 오류는 관찰/우선순위를, 사실 오류는 데이터/검증을, 해석 오류는 모델/분석 정책을, 조사 누락은 검색/도구를 보완합니다. 미사용 주차로 다시 확인합니다.

완료 조건: 개선 원인과 남은 한계가 설명되고, 미사용 주차에서도 핵심 재작성 부담이 줄어듦.
STEP 04

실제 주간 운영과 제품 화면으로 연결

앞으로의 주차를 사전에 고정해 평가하고 실행 상태·원문·지난 판단·수정 이력을 기존 읽기 경험에 연결합니다. 반복적으로 필요한 수집기와 병렬 조사는 실측 근거로 편입합니다. 발행/예약은 별도 운영 결정 이후 연결합니다.

완료 조건: 반복 품질·수정 부담·실행 신뢰성·비용을 함께 확인. 시장 상태가 달라지는 주차의 실패도 공개적으로 기록.

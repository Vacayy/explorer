# 링크 스크랩 — URL만 올리는 채널의 원문 확장 + 미검증 소스 격리 (2026-09-09)

> 상태: **구현됨 (D-142)**. 계기: '비나인의 블로그 스크랩' 텔레그램 채널.
> 관련: PHILOSOPHY §1(사실/가설 분리 비타협) · §4(기계는 제안, 사람이 판단) · D-004 ③(에코챔버 방지) · D-095(스터디 후보 프레이밍) · D-126(수집/노출 축 분리) · docs/specs/chat-agent.md(도구 카탈로그)

---

## 0. 한 문장

**"링크를 따라가 원문을 문서로 만들되, 그 문서는 월드모델·신호·기본 검색에 들어가지 못하게 하고 읽히는 자리마다 미검증이라 밝힌다."**

## 1. 문제

'비나인의 블로그 스크랩'은 좋은 블로그 글을 URL로만 모아 올리는 채널이다. 한국 투자자들이 실제로 무엇을 스터디하는지 드러나는 고신호 소스인데, 시스템에서는 죽어 있었다.

| 항목 | 실측 (2026-09-09) |
|---|---|
| 저장된 문서 | 11건, `source_type='telegram'`, 제목이 URL 그 자체 |
| 본문 | 44~230자, 네이버 블로그 링크 1~3개뿐 |
| 유입 | 하루 약 4건, URL 기준 약 7개 |

본문이 URL뿐이라 enrich가 태깅할 것이 없고, 엔티티 링크·청크·검색·대화가 전부 빈손이었다.

## 2. 두 번째 문제 — 섞이면 안 된다

원문을 가져오면 곧바로 인식론 문제가 생긴다. 이건 **사실관계가 확인되지 않은 개인 투자자의 주장**이고, 공시·컨콜·증권사 리포트와 같은 근거 풀에 섞이면 월드모델이 "그럴듯한 쓰레기"가 된다(PHILOSOPHY §1).

**"라벨만 잘 붙이면 LLM이 알아서 하지 않나"는 절반만 맞다.** 라벨이 통하는 자리와 통하지 않는 자리가 갈린다.

| 경로 | 라벨이 통하나 | 이유 |
|---|---|---|
| 대화 종합 | ○ | 청크 접두어 `[소스·날짜]`가 BM25·벡터 양쪽에 이미 실린다 |
| 종목 다이제스트 | ○ | 문서마다 `[source_type]`을 컨텍스트에 이미 붙인다 |
| **인과 추출**(`doc_causal`) | ✗ | enrich된 문서면 소스 무관하게 엣지를 뽑는다. 블로거 주장이 월드모델 엣지가 된다 |
| **내러티브 생성**(`narrative`) | ✗ | 프롬프트에 라벨은 붙지만, 거기서 나온 엣지는 결국 같은 그래프로 들어간다 |
| **지식 승격**(`promote_causal_edges`) | ✗ | 2+ 내러티브가 다른 날 반복 주장하면 지식으로 승격되고, 승격된 지식은 다음 생성에 전제로 재주입된다. 스크랩끼리 서로를 뒷받침하면 고리가 닫힌다 |
| **언급 급증**(`signals`) | ✗ | 엔티티 링크 수만 센다. 리테일 잡담과 증권사 커버리지가 같은 한 건 |
| **검색 랭킹**(`rag`) | ✗ | 소스 가중치가 없다. 스크랩 청크가 컨콜 청크와 동등하게 경쟁한다 |

라벨을 읽을 주체가 없는 코드 경로가 오염의 본체다. 그래서 **차단은 코드로, 라벨은 남는 자리에**.

## 3. 획득 — 링크 확장

`pipeline/connectors/scrap.py` · `source_type='scrap'`

- **옵트인**: `telegram_channels.expand_links=1`인 채널만. 모든 채널의 모든 URL을 따라가면 뉴스 인용 링크까지 긁어와 노이즈가 폭증한다.
- **URL 하나 = 문서 하나**. `source_id=url`이라 같은 글이 여러 번 스크랩돼도 문서는 하나. 한 메시지에 서로 다른 종목 글이 여러 개 오므로 메시지에 합치면 엔티티 링크·청킹이 뒤섞인다.
- **본문**: 기존 `services/blog_service.fetch_full_content()` 재사용. 네이버 블로그 iframe 구조를 이미 처리한다(실측: 8,117자·126,007자 정상 획득). 실패하면 `None`을 돌려주므로 임의 URL에도 안전하다.
- **제목·작성자**: `og:title` + `naverblog:nickname`. 실측 "아이센스 주담통화 · 버핏키즈", "대한항공 기업분석(feat.항공화물 운임) · 또치".
- **발행일**: 원문 발행일 메타가 없어 **스크랩된 메시지 시각**으로 근사한다. 사람들이 갓 올라온 글을 스크랩하므로 오차가 작지만, 정확한 발행일이 아님을 여기 남긴다.
- **상한**: 본문 30,000자(청크 상한 문서당 80 대응) · 회차당 20링크 · 요청 간격 1초 · 실패 재시도 3회.
- **제외**: `t.me`·유튜브·X(다른 커넥터 담당) · 이미지/PDF 확장자 · 이미 구독 블로그로 수집된 URL(`status='duplicate'`).

**대장 `scrap_links`** — url(PK) · doc_id · channel · src_doc_id · seen_count · status(pending|ok|failed|duplicate) · tries · first_seen_at · last_seen_at. `seen_count`가 반복 노출을 세므로 훗날 "여러 번 스크랩된 글" 신호의 재료가 된다.

**runner 훅**: `run_source`가 store 후 커넥터의 선택적 `after_store(doc, result)`를 부른다. 스크랩은 이걸로 doc_id를 대장에 되쓴다. 다른 커넥터에는 영향 없음.

크론 편입은 자동이다. `scripts/ingest.py`가 등록된 커넥터를 전부 돌고, 레지스트리에서 scrap이 telegram 뒤에 있어 같은 회차에서 방금 수집한 메시지를 읽는다.

## 4. 격리 — 판정은 한 곳에서

`pipeline/visibility.UNVERIFIED_SOURCES = {"scrap"}` 하나가 진실원천이고, 다섯 경로가 이것을 임포트한다. 비슷한 소스가 늘어도 한 줄만 바뀐다.

| 차단 지점 | 방식 |
|---|---|
| `doc_causal._candidates` · `extract_for_doc` | `unverified_sql()`로 WHERE 제외 — 월드모델 문 ① |
| `narrative._topic_docs` | 〃 — 월드모델 문 ② (엣지·지식 승격의 상류) |
| `signals.compute_mention_surge` | 〃 — 리테일 잡담이 커버리지 언급으로 집계되지 않게 |
| `rag.retrieve_docs` | `source` 미지정이면 결과에서 제외 — 기본 검색 풀에서 뺀다 |
| `list_recent(kind=docs)` | `unverified_sql()` (D-143 보강 — raw_documents를 직접 훑는 다섯 번째 경로였다. 채널을 이름으로 지목하면 명시적 요청이라 통과) |

**검색은 전용 문으로만.** `search_docs(source='scrap')`로 명시할 때만 조회된다. 라우터 프롬프트에 "다른 투자자들은 뭐라고 하나·요즘 뭘 스터디하나·개인 블로그 시각을 묻는 질문에만" 규칙을 넣었다. 원하는 가치는 더 많은 사실이 아니라 남들의 생각이므로 질문 유형이 다르면 문도 달라야 한다. 답변에 스크랩이 섞이는 순간은 곧 사용자가 그걸 의도한 순간이다.

## 5. 라벨 — 남는 자리

- **청크 접두어**: `[스크랩(미검증)·날짜] 제목 — 요약`. BM25·벡터 양쪽에 실려 종합이 근거 텍스트로 읽는다.
- **종합 프롬프트 규칙**: "'스크랩(미검증)' 라벨이 붙은 근거는 개인 투자자 블로그의 주장이다. 사실로 단언하지 말고 '이렇게 보는 시각이 있다'는 형태로만 쓰고, 누구의 주장인지 밝힌다. 시세·공시와 어긋나면 후자를 따른다."
- **도구 카탈로그**: `search_docs`의 source 인자 설명에 scrap의 성격과 사용 조건을 명시.
- **화면**: 피드 `스크랩` 탭(맨 뒤) + `SourceBadge`가 "스크랩 · 미검증"을 **hypothesis 색 아웃라인**으로 표시. 출처는 스크랩한 채널로 귀속되고 블로거 이름은 제목에 붙는다.

## 5-1. 도달 경로 (D-143)

스크랩에 닿는 문은 셋이다. 전부 사용자가 명시해야 열린다.

- `search_docs(source='scrap')` — 주제로 찾을 때.
- `list_recent(kind='scrap')` — "최근 스크랩된 글" 같은 목록 질문. 검색으로는 안 잡히는 유형이다.
- `list_recent(kind='docs', channel='비나인')` — 스크랩 채널을 이름으로 부를 때. `_match_sources`가 `scrap_links.channel`을 타고 원문까지 매칭한다. 링크만 든 원본 메시지는 컨테이너로 보고 뺀다.

## 6. 5-state

스크랩은 수집 계층이라 화면 상태는 피드 탭이 상속한다. 커넥터 자체의 상태는 대장이 갖는다: pending(등록만) · ok · failed(3회까지 재시도) · duplicate(구독 블로그로 이미 수집됨).

## 7. 기각한 대안

- **원문을 텔레그램 메시지 문서에 합치기** — 한 메시지에 서로 다른 종목 글이 여러 개라 문서가 뒤섞인다. 엔티티 링크와 청킹이 망가진다.
- **`source_type='blog'`로 저장 + 블로거 자동 등록** — 피드의 블로그·뉴스·아티클 탭과 소스 필터는 등록된 `blog_sources`만 훑어서, 등록하지 않으면 보이지 않고 등록하면 팔로우 레일이 한 번 스치고 마는 블로거 수백 명으로 찬다. 팔로우는 사람이 고른다(§4).
- **모든 채널의 URL 확장** — 뉴스 인용 링크·유료 기사까지 긁혀 노이즈와 요청량이 폭증. 옵트인 플래그로 대체.
- **라벨만 붙이고 전부 섞기** — §2의 표. 코드 경로에는 라벨을 읽을 주체가 없다.
- **아예 수집하지 않기** — 무엇을 스터디하는지가 이 채널의 가치다. 문제는 획득이 아니라 전파다.

## 8. 후속

- **스터디 열기 신호**: 스크랩 문서도 엔티티 링크를 받으므로 "최근 7일 스크랩 글에서 가장 많이 언급된 종목"이 쿼리 하나로 나온다. D-095의 스터디 후보와 같은 자리. 데이터가 쌓인 뒤 홈 신호로.
- **블로거 승격 후보**: 반복해서 좋은 글을 쓰는 작성자를 구독 블로그 승격 제안으로(승인 큐, `entity_alias` 선례와 같은 형태). 지금은 작성자 이름만 제목에 남겨둔다.
- **`seen_count` 활용**: 여러 번 스크랩된 글 = 여러 사람이 주목한 글.

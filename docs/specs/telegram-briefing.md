# 텔레그램 아침 브리핑 v2 — 읽는 브리핑에서 **누르는 브리핑**으로

> 상태: 구현 (D-107) · 관련: D-106(발송 신뢰성·launchd) · D-095~097(미국장 브리핑) · D-028(내러티브)

## 1. 문제

v1 브리핑은 초창기(D-056) 재료에 멈춰 있었다 — `기계의 3줄` + 오늘 일정 + 업데이트 **건수**뿐,
실측 155~322자. 그 사이 홈은 어젯밤 미국장 브리핑(D-095~097)·시장 국면(D-076)·매크로 유동성(D-101)으로
크게 자랐는데 텔레그램은 따라가지 않았다. 정작 출근길 폰에서 가장 값진 게 미국장 브리핑인데 빠져 있었다.

또한 v1은 **읽고 끝**이었다. "홈에서 확인"이라 써놓고 링크는 로컬(`localhost:5173`)이라 폰에서 열리지 않는다.
가방 속 랩탑 앞에 앉기 전까지 브리핑은 죽은 텍스트였다.

## 2. 방향

브리핑을 **작업 착수점**으로 만든다. 관심 가는 항목을 그 자리에서 눌러 생성을 걸어두면,
결과가 다시 텔레그램으로 온다. 도구 앞에 앉기 전에 판단 재료가 준비된다.

- 새 파이프라인을 만들지 않는다 — 기존 생성 로직(`compute_narrative`, 유튜브 lazy digest)을 **그대로 호출**한다.
- 브리핑 조립 자체는 **LLM 0콜**. 미국장 종합은 이미 캐시된 것(`us_briefings`)을 읽기만 한다.
- 비싼 생성은 **사람이 누른 것만** (D-020 계승 — 제안 먼저, 노동은 승인 뒤).

### 주제 top 5 = 최다 3 + 급상승 2 (사용자 확정)

절대 최다만 쓰면 매일 같은 얼굴(AI·반도체·자동차)이고, 급상승(`theme_surge`)만 쓰면
"어제 무엇이 화두였나"라는 물음에 답하지 않는다. 둘을 섞어 **판의 크기와 변화**를 함께 준다.

- **최다 3**: 어제(24h) 문서에 `entity_links(link_type IN industry|topic)`로 붙은 `theme`·`sector` 노드의
  DISTINCT 문서 수 상위 3. `signals.THEME_STOPWORDS`(산업동향·실적분석·밸류에이션·수급 등 **문서유형 메타 라벨**)를
  반드시 제외 — 제외하지 않으면 상위를 라벨이 독식한다(실측: 산업동향 127 · 실적분석 80 · 밸류에이션 53).
- **급상승 2**: 최신 `theme_surge` 신호를 `share_delta_pp` 내림차순, 최다 3과 중복 제거 후 2개.

## 4. 인터랙션

### 버튼 → 콜백

| 버튼 | `callback_data` | 동작 |
|---|---|---|
| 🧠 주제 | `n:{entity_id}` | `compute_narrative(name)` — 문서집합 불변이면 캐시 반환(멱등) |
| 📺 영상 | `y:{doc_id}` | `spine_doc.get_document(doc_id)` — 유튜브면 digest 미완성 시 그 자리에서 opus 재시도 |

`callback_data`는 64바이트 상한이라 **이름이 아닌 id**를 싣는다.

### 응답 규약

생성은 opus라 수십 초~수 분이다. 텔레그램은 콜백을 몇 초 안에 ack하지 않으면 버튼이 멈춘 것처럼 보인다:

1. `answerCallbackQuery` 즉시 (토스트: "생성 시작 — 완료되면 보내드립니다")
2. "🧠 'AI' 내러티브 생성 중… 1~2분 걸립니다" 선응답
3. **데몬 스레드**에서 생성 → 완료 시 결과 메시지 (폴링 루프를 막지 않는다)

동시 실행은 주제/문서 단위로 잠근다(`_inflight`) — 연타로 opus가 중복 기동되지 않게.

### 제약 (알고 쓰는 것)

버튼 처리는 **백엔드 서버가 떠 있을 때만** 동작한다(봇 폴링이 FastAPI startup 스레드, `bot.py`).
발송은 launchd라 서버와 무관하지만, 콜백은 그렇지 않다. 랩탑이 가방에 있는 동안 누른 버튼은
텔레그램이 `getUpdates` 백로그에 최대 24시간 보관하므로 **서버가 켜지는 즉시 처리**되어 결과가 온다.
즉 "지금 즉시"는 보장 못 해도 "유실"은 없다. 이 지연은 설계상 수용한다 — 대안(콜백을 launchd 폴러로 이중화)은
같은 봇 토큰에 `getUpdates` 소비자가 둘이 되어 업데이트를 서로 훔친다.

## 5. 5-state

브리핑은 화면이 아니지만 같은 규율을 적용한다.

| 상태 | 처리 |
|---|---|
| Empty | 모든 섹션이 비면 발송하지 않는다(`_compose_briefing() → None`, `job_runs=skipped`) |
| Loading | 콜백 선응답("생성 중… 1~2분") |
| Partial | 섹션 단위 독립 — 미국장 종합이 없으면(캐시 미생성·LLM 미가용) 그 섹션만 스켈레톤(쏠림·이슈)으로, 유튜브 0건이면 섹션 생략 |
| Error | 생성 실패 시 사유를 그대로 회신("문서 3건 미만이라 생성 불가" 등 status별 문구). 발송 실패는 3회 재시도 후 `job_runs=error` → 체인 캐치업이 재시도(D-106) |
| Ideal | 위 §3 |

## 6. 비용

| 항목 | LLM |
|---|---|
| 브리핑 조립(주제 집계·유튜브 목록·미국장 읽기) | **0콜** — 전부 SQL + 캐시 읽기 |
| 미국장 종합 | 0콜 (홈이 이미 만든 `us_briefings` 캐시를 읽기만. 없으면 생략) |
| 주제 버튼 | opus 1콜 / 누른 것만 · 문서집합 불변이면 0콜(캐시) |
| 유튜브 버튼 | opus 1콜 / 누른 것만 · 이미 `digest_status='ok'`면 0콜 |

일일 고정비는 0이고, 변동비는 사람이 누른 만큼만 — 비용 의식 설계(D-072) 유지.

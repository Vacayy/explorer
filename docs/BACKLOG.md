## 핵심질문↔프록시 트랙 (2026-07-26 착수 — D-067·D-068, 스펙: docs/specs/question-proxy.md)

> 리포트 핵심질문(D-049)과 transcript 프록시(D-061)를 분할정복으로 잇는 질문 트래커.
> Phase 1 착수(데이터 모델+사용자 주입 생성자+numeric 프록시+결정적 판정+지식 탭 뷰).
> 아래는 스펙 §미해결에서 이관한 **Phase 밖 후속** — 셋 다 Phase 1을 막지 않음(데이터·정밀도 이슈).

**Q5 라이브 테스트로 드러난 갭 (2026-07-26, SK하이퍼 문서 딥다이브)**
- **한국 종목 질문의 numeric 프록시가 영원히 미판정** — numeric 추출기가 미국 컨콜(transcripts)만 읽어, 한국
  기업(SKT·HD현대일렉트릭 등) 프록시는 매칭 소스가 없어 confirm=unknown 고착. → **재무·컨센서스 추출기(Phase 1.5,
  스펙에 이미 명시)가 실제 병목으로 부상.** Korean-stock 질문엔 지금 sentiment(코퍼스)만 작동.
- **Q5 모달 UX = fire-and-forget 필요** — 분해·추적이 수 분~십수 분인데 모달에서 대기를 강제. 게다가 api 클라이언트
  timeout 무한이라 서버 완료 후에도 스피너가 안 풀림. → 즉시 닫고 지식 탭에서 확인하는 흐름 + 진행상태 폴링으로 재설계.
- **doc-derived 시나리오 영속 뷰 부재** — Q5 시나리오는 scenarios 테이블에 캐시되나 모달 인라인으로만 렌더. 닫으면
  다시 볼 FE 화면이 없음(GET /narrative/scenario?topic=event API만). 시나리오 열람 라우트 필요.

**미결 (Phase 밖 후속)**
- **전망 정박 (미래 활용, D-073 후속)** — 내러티브 전망 섹션·리포트 thesis·시나리오를 관련 질문의 판정(2층 verdict)에
  정박(전망→질문 링크). 지금은 매번 LLM이 새로 단언 → 추적·반증 안 됨. 질문에 여러 분기 verdict가 쌓인 뒤 착수.
  승격(질문→지식, 과거화)보다 당장 가치 클 수 있음(미판정인 채로도 전망에 정직한 근거 부여).
- **섹터 단위 집약 (D-074, 설계 정박 완료 → 구현 대기)** — docs/specs/sector-aggregation.md. 유니버스 그룹=섹터,
  집약 뷰(N:M), 리포트 앵커 topic→그룹, /follow/universe 증강. **Phase 1**(그룹→내러티브 집약 API+유니버스 노출,
  LLM 0·저위험, 첫 수확)→**2**(섹터 리포트)→**3**(편입 고리). 구현 착수만 남음.
- **서브질문 → 지식 승격 conviction 임계** — 질문 verdict가 얼마나 확고해야(confirm_verdict 확정 + lead 동조 +
  독립 관측 N회) 검증 지식으로 승격하나. 지식 사다리(K0 consolidation) 재사용이 전제이나 "질문→지식" 승격의
  임계·독립성 규칙은 미정. 질문이 실제 판정되며 관측이 쌓인 뒤 실데이터로 튜닝(지금 정하면 거짓 정밀).
- **프록시 관측 독립성** — sentiment 프록시(여론)가 말뭉치 복제편향(보도자료 1→기사 10→블로그 20)에 부풀 위험.
  D-065 한계 5(relation_evidence·independence_group 미해결)와 **동일 근본 문제** — 어느 문서가 한 원천 계보인가의
  독립성 탐지가 선결. 그게 풀리기 전엔 sentiment 프록시 방향은 참고치, confirm(numeric)이 판정 앵커.
- **stance 프록시 데이터** — "수장이 보수적으로 돌아서나"(발언 태세 변화) 추적은 person 발언 감성 **시계열**이 선결.
  현재 감성 태깅은 있으나 인물별 시계열로 프록시화 안 됨. Phase 3(stance modality)에서 person 감성 축적 후.

  ② 레이어 분리(권장) — 수집·인과그래프·내러티브·지식(룰 기반 게이트를 거치는 "공공재" 층)은
  공유 인스턴스 하나로 유지, 대화·질문·워치리스트 등 개인화가 새는 지점만 `user_id` 스코프.
  수집 파이프라인은 1회만 돌려 비용 공유, 판단 계층만 사람별로 격리.
  cf. 진화계획 2단계(product-v3.md, "질문의 cron화")는 반복 질문을 브리핑에 편입하는데,
  다중 사용자 환경에선 이게 user_id 스코프 없이 전역으로 새면 한 사람의 관심사가 남의
  피드에 노출되는 문제와 직결 — 배포 결정 전에 이 설계를 먼저 확정해야 함.

# Engineering playbooks

pstack의 버그 수정·리팩토링·조사 플레이북을 이 프로젝트에 맞게 줄인 것이다. 원칙은 글로벌 CLAUDE.md(§1 생각 먼저, §2 단순함, §3 수술적 변경, §4 목표 주도)와 프로젝트 CLAUDE.md의 Integrity Rules가 담당한다. 이 문서는 절차만 정한다.

## 공통 규칙

- **지도부터.** docs/SYSTEM.md의 해당 절을 읽고, graft로 위치를 잡은 뒤(`graft ask "<질문>"`, `graft callers <symbol>`, `graft grep "<리터럴>"`) 소스를 연다.
- **이유는 기록에서.** "왜 이렇게 돼 있나"는 docs/DECISIONS.md와 `git log`로 답한다. pstack의 `why` 스킬은 이 두 곳이 대신한다.
- **기본은 직접 작업.** 서브에이전트는 읽기 전용 탐색 팬아웃(Explore)이나 기계적 대량 편집에만 쓴다. 위임했으면 diff를 직접 검토하고 요약을 그대로 전달하지 않는다.
- **검증 표면.** 백엔드는 `python -c "from main import app"`, `../.venv/bin/python -m unittest discover -s tests`(backend/에서), 필요하면 uvicorn 기동 후 curl. 프론트엔드는 `npx tsc --noEmit`, `node --test frontend/tests/*.test.mjs`, 실제 화면 확인. "컴파일된다"는 검증이 아니다.
- **커밋.** development 브랜치에 작은 단위로 직접 커밋한다. 메시지는 한국어(글로벌 CLAUDE.md §5). PR 절차는 없다.
- **문서 동기화.** 구조가 바뀌면 SYSTEM.md를 같은 커밋에서, 대안을 기각한 결정이면 DECISIONS.md에 항목을 추가한다(프로젝트 CLAUDE.md Context Discipline).
- **응답.** `unslop` 스킬을 적용한다. 재현 출력과 테스트 결과는 요약하지 말고 원문을 붙인다.

## 조사 (Investigation)

읽기 전용이다. 결과물은 인용된 설명이나 추천이고, 코드 변경이 아니다.

1. `how` 스킬로 답한다. 단일 모듈이면 직접 읽고 설명하고, 여러 파일을 가로지르면 Explore 팬아웃 후 종합한다.
2. 산출 형식은 Overview / Key Concepts / How It Works / Where Things Live / Gotchas. 대안 사이의 결정이면 트레이드오프 표와 추천 하나.
3. "확실해?"에는 근거와 함께 실제 판단을 말한다. 전제가 틀렸으면 반박한다.
4. 조사가 코드 변경으로 이어지면 여기서 멈추고 버그 수정, 리팩토링, 또는 product-orchestrator로 다시 들어간다.

## 버그 수정 (Bug fix)

과학적으로 한다. 배포되는 모든 줄은 런타임 근거에 연결된다. "도움이 될지도 모르는" 방어 코드는 가설이고, 가설은 배포하지 않는다. 근거가 가설을 반박하면 그 가설이 만든 코드를 되돌린다.

1. **직접 재현한다.** 실제 표면에서 한다. 사용자에게 재현을 넘기지 않는다. 바로 재현되지 않으면 조건을 좁히거나 로그를 심어 강제로 발생시킨다.
2. **원인을 이분 탐색한다.** 후보 가설을 세우고 런타임 근거로 하나씩 소거한다. 서브시스템 파악은 `how`, 회귀 이력은 DECISIONS.md와 `git log -p`. 상태가 불분명하면 추측하지 말고 계측을 추가해 읽는다. 메커니즘을 런타임으로 확인한 뒤에 수정을 설계한다.
3. **수정을 계획한다.** 함수 경계를 넘는 변경이면 호출자 쪽 사용법과 타입을 먼저 정한다. 근거가 정당화하는 최소 변경만 한다.
4. **같은 표면에서 검증한다.** 1번의 재현이 이제 통과해야 한다. 애매하면 통과가 아니다. 단위 테스트는 분기 동작을 보여줄 뿐 버그 부재를 증명하지 않는다.
5. **커밋 순서는 실패 테스트가 먼저, 수정이 다음.** 싼 로컬 테스트 경로가 있으면 `tdd` 스킬을 따른다. 없으면 그 이유를 말하고 가장 가까운 실행 가능한 검증(스크립트, curl, 브라우저 확인)으로 대체한다.
6. 수정이 공유 코드에 닿으면 `blast-radius`로 다른 곳 파급을 확인한다.

**응답:** 무엇이 깨졌나, 근본 원인, 수정, 검증 방법. 실패했다가 통과한 재현 출력을 그대로 붙인다.

## 리팩토링 (Refactoring)

구조는 바뀌고 동작은 바뀌지 않는다. 정리 중에 빠진 기능이나 진짜 버그가 보이면 분리해서 구조 변경을 먼저 끝낸다. 재설계가 필요하면 그렇다고 말하고 product-orchestrator로 보낸다.

1. **동작 계약을 먼저 고정한다.** `how`로 계약을 파악한 뒤 특성화 테스트, 스냅샷, 또는 등가 하네스로 현재 동작을 잡아둔다. 커버리지가 없으면 구조를 건드리기 전에 만든다. tsc와 lint는 핀이 아니다.
2. **목표 형태를 이름 붙인다.** 오늘 처음 만든다면 모듈 배치, 타입, 호출 그래프가 어떠해야 하는지 말한다. 재구성은 분기나 불법 상태를 지워야 하고, 간접층을 더하면 안 된다.
3. **빼기 먼저.** 죽은 코드, 호출자가 하나인 래퍼, 중복 검증기, 고아 참조를 먼저 제거하고 그 위에 새 형태를 올린다.
4. **작은 동작 보존 단계로 옮긴다.** 매 단계 핀이 green이어야 한다. API 재구성은 모든 호출자 이전과 구 API 삭제를 같은 커밋에 넣는다. 호환 shim이나 old/new 병행 경로를 남기지 않는다. 이름 변경은 문자열, 문서, `graft callers`로 누락을 확인한다.
5. **실제 산출물로 동작 불변을 증명한다.** 큰 재구성은 old/new 출력을 diff하는 스크립트나 기록된 baseline 재생으로 한다. 위임했다면 "괜찮아 보인다"는 요약을 믿지 말고 직접 돌린다.
6. **유지 가치를 확인한다.** 성공 기준은 읽는 사람의 부담 감소다. diff가 어디서도 부담을 낮추지 않으면 되돌린다.
7. **커밋은 빼기, 재구성, 후속 정리 순서.** 설계가 논쟁적이면 배포 전에 `interrogate`.

**응답:** 바뀐 구조, 고정했던 핀, 등가 증명, 읽기 부담의 변화, 배포한 것과 되돌린 것. 새 동작은 없다.

## 진입점 구분

| 요청 | 사용 |
|---|---|
| 새 기능, 새 화면, 새 API, 다분야 작업 | product-orchestrator (CLAUDE.md) |
| 버그 수정, 리팩토링, 조사 | 이 문서 |
| 단일 파일의 사소한 수정 | 플레이북 없이 직접. 검증 표면만 지킨다 |

글로벌 스킬(`how`, `blast-radius`, `tdd`, `interrogate`, `unslop`)이 설치되지 않은 환경이면 해당 단계를 같은 의도로 직접 수행한다.
